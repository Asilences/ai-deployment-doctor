# 两槽位历史反馈开发实验：执行前协议

上一轮单槽位试点无法检验利用候选失败历史；其 `no_feedback` 还同时移除了当前测量。本轮新增 `no_history`，保持当前配置的吞吐、延迟以及完整环境 / 负载，只把 `prior_trials` 置空。原 `no_feedback` 语义不变。

## 设计与控制

使用同一 1.5B Qwen 模型、temperature=0、generation seed=42、300 completion token 上限、v3.1 有界解释输出；候选 ID、未试候选约束、单槽规划服务及外部 verifier 全部不变。新消融模块有独立源码哈希，不回填旧运行。

先只运行已有 prefill 开发任务：24 请求、384/32 token、并发 8，从 `(parallel=2, ubatch_size=128)` 独立开始；full 与 no_history 各两个提案槽位、每槽位最多两次模型调用。计划种子 20260930 在运行前决定顺序。批次上限 900 秒，完成当前验证 / 恢复后安全停止；每项运行结束独立 final，不比较不同槽位上限的历史分数。

```powershell
python -B scripts/run_context_pilot.py --tasks prefill --methods full no_history --iterations 2 --order-seed 20260930 --max-seconds 900
```

第一槽位输入结构一致，历史均为空；第二槽位 full 获得第一轮候选 ID、配置、接受、收益与原因，no_history 的历史仍为空。两者保留当前指标、当前配置与合法未试目录；目录透露访问过的配置，因此不是完全抹除历史。若第一项被保留，no_history 仍看见新 incumbent 及其测量，这也是共同约束 / 状态信息。

每项 baseline 都独立重新测量。因此首项数值不完全相同，即使提示结构一致，也不是完全相同的输入。记录首项选择是否相同；不同初始选择时，后续差异同时包含轨迹差异，不能单独归因于历史字段。此设计是闭环开发诊断，不是严格的同状态反事实因果检验。

## 指标与判别

保留两个提案、真实输入 evidence、每次调用 / 纠错 / token、候选执行、失败、恢复、最终配置及独立 final。检查第二轮排除已执行候选；full 的真实失败记录与第一轮一致，no_history 无历史文本、仍有当前指标。

假设：full 能依据第一轮测量形成下一项更有用的选择。若它忽略失败、仅机械选择剩余首项、产生错误的已测最高性能说法、或最终结果不如 no_history，则不支持该假设。不同 ID 本身不能证明有用推理；合法未试约束造成的“不重复”也不能算模型学会了纠错。

单任务、两个方法各一次轨迹不足以证明统计优势、RSI 能力改善、L4 或 L5。本轮暂不跑完整随机 / 固定规则两槽位对照；旧单槽位试点只能作为不同预算的背景，不用于本轮方法差值。后续只有机制诊断值得继续时才冻结多任务完整块。

两个新增受控测试检查：首槽位结构相同；后续真实请求只移除语义历史、保留指标及相同可用列表 / schema。54 项测试通过。结果单独追加，不覆盖此前失败与单槽位对照。
