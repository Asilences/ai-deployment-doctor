# 首轮真实推理实验：2026-09-24

## 问题与环境

研究问题：在固定目标、负载和验收规则下，固定权重的本地模型能否根据推理服务的测量结果，自主选择下一项配置实验，并将验证有效的更改留给后续轮次？

- 硬件：RTX 3070 Ti Laptop GPU，8 GB 显存；Windows 本机。
- 服务：[llama.cpp b11138](https://github.com/ggml-org/llama.cpp/releases/tag/b11138)，Vulkan GPU 后端。
- 模型：[Qwen2.5-1.5B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF)，Q4_K_M，提交 `91cad51170dc346986eccefdc2dd33a9da36ead9`，文件 SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`。
- 规划器：同一固定权重模型，通过本地 HTTP 接口读取结构化测量结果并输出 JSON 候选。
- 固定负载：16 个请求；每个 128 输入 token、32 输出 token；客户端并发 8。每次重启后统一预热；参考和候选交替，各测三次。
- 优化目标：在请求全部成功、输出完整和 p95 延迟满足配置文件固定门槛时，提高总输出 token/秒。候选中位数相对参考须提升至少 5%，且候选三次的最低吞吐超过参考三次的最高吞吐；功能冒烟测试输出保持一致。保留前还需重启复核。

## 结果

| 一次实验预算 | 提出的配置 `(parallel, ubatch_size)` | 参考吞吐中位数 | 候选吞吐中位数 | 验收 |
| --- | --- | ---: | ---: | --- |
| 本地模型自主提案 | `(4, 512)` | 247.07 token/s | 321.01 token/s | +29.9%；通过并保存 |
| 固定随机种子对照 | `(8, 64)` | 258.73 token/s | 270.41 token/s | +4.5%；低于 5% 门槛，恢复参考配置 |
| 继承后的本地模型第二轮 | `(2, 64)` | 315.16 token/s | 238.41 token/s | -24.4%；拒绝候选，重启恢复 `(4, 512)` |

本地模型提出的假设是提高并行度及物理批处理大小可能提高吞吐并降低延迟。程序只接受两个允许范围内的整数参数；提案无法修改目标函数、压测请求或验收器。该提案三次候选吞吐分别为 313.60、321.01、322.59 token/s；对应参考为 240.74、255.16、247.07 token/s。候选通过了全部请求、固定输入输出长度、三个固定 prompt 的输出一致性以及延迟检查。保存前重启检查结果为 `promotion_restart_verified`。

新的独立运行加载保存的 `best.json`，保留配置仍为 `(4, 512)`，代数为 1，历史记录为 1 条；三次复测吞吐为 323.45、320.74、316.56 token/s，中位数 320.74 token/s。模型权重始终没有变化。

随后启动有一次新提案预算的继承轮次。本地模型根据已保存状态提出 `(2, 64)`；候选中位吞吐 238.41 token/s，参考 315.16 token/s，下降 24.4%。系统拒绝该候选，重启后验证原配置，最终 `best.json` 仍为 `(4, 512)`、代数 1。小模型曾出现一次提案格式无效，控制器没有执行该提案；现在本地规划器最多允许一次纠错重试。重试不改变候选参数的范围和外部验收规则。

## 解释范围

结果支持一个**有边界的 training-free L2 工程演示**：Agent 在外部固定目标和验收规则下，自主选择配置修改；系统通过真实反馈验收，并把改进配置用于后续轮次。第二轮还显示负反馈会阻止退步候选覆盖已保存状态。这不表示开放式 RSI，也不表示 Agent 已改进自身的搜索算法。不同运行的参考吞吐有差异，单次随机种子对照不足以证明本地模型普遍优于随机搜索。

负载仅 16 个请求，p95 接近最大值，对运行噪声敏感；三个固定 prompt 只是功能冒烟测试，未验证语义质量或未知工作负载。后续研究应冻结更大规模的训练/测试负载划分、重复不同随机种子和同预算对照，再评估跨负载泛化。OpenRouter 路线因尚无实验室 API Key 未运行。
