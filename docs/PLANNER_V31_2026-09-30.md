# v3.1：约束解释长度的独立开发验证

此前 v3 的两个任务共 8 次调用均达到 300 completion token 上限，并输出未闭合 JSON。失败记录保留在 [工作日志](WORKLOG_2026-09-30.md)，不覆盖。

v3.1 继续要求模型自主返回 `candidate_id`、`hypothesis`、`expected_effect`；JSON Schema 对两个解释字段设置 `minLength=1, maxLength=96`，系统提示要求短句，控制器解析也独立验证上限。超过上限直接拒绝，不截断文本、修补 JSON 或代选 ID。总生成预算仍为 300 token，温度 0、seed 42、候选目录与固定提案服务不变。

固定版本 llama.cpp b11138 的 [官方 grammar integration tests](https://github.com/ggml-org/llama.cpp/blob/b11138/tests/test-grammar-integration.cpp) 包含 string min/max length 测试。因此使用引擎既有的受约束生成能力，不修改引擎或验收器。长度约束限制生成格式，不能证明解释正确或搜索更有效。

账本新增 `finish_reason` 和 `generation_limit_reached`；缺失时未知。历史记录不回填。v2 和 v3 的提案格式保持原有语义；v3.1 通过 `--planner-version v3.1` 显式启用。

## 首项开发验证（执行前记录）

- 假设：两个解释字段限制为 96 字符，可在原生成预算内输出完整合法 JSON。
- 自变量：输出 schema 的长度约束及相应简短提示；不能把作用单独归因于 schema。
- 控制：原模型、低并发开发负载、配置空间、起点、单槽位规划服务、生成 token 上限及固定 verifier。
- 预算：低并发一个提案槽位，至多一次纠错，共至多两次调用；时间上限 900 秒。搜索结束后独立 final。
- 指标：完整 JSON、字段长度、合法未试 ID、finish_reason、调用 / token 成本、候选执行及拒绝 / 恢复结果。
- 判别：完整提案足以进入真实候选验证；候选即使无收益也不能否定输出完成假设。
- 可证伪结果：预算内仍无有效提案。停止并记录原因，不通过提高性能阈值的宽松度制造成功。

```powershell
python -B scripts/run_v3_smoke.py --planner-version v3.1 --tasks serial --iterations 1 --max-seconds 900
```

这是已用开发任务上的工程诊断，不是 v3/v3.1 的无偏成功率比较、环境感知消融或 holdout。

测试：新增长度 schema 检查、解析拒绝超长字段且不截断、v3 原 schema 不变及 finish_reason 记录；共 47 项测试通过。实际记录完成后追加到工作日志。

实测追加入口：[工作日志](WORKLOG_2026-09-30.md)记录首项合法输出、941 token、候选拒绝与恢复；随后新增消融工具，52 项测试通过，[开发结果](CONTEXT_RESULTS_2026-09-30.md)保留完整信息版本未优于简单对照的负结果。不同源码身份的运行不混合为一个性能平均值。
